Coming from SciPy

If you have a right-hand-side function written for scipy.integrate.solve_ivp, cubie can usually run it unchanged. The main differences are in how you pass the parameters and the time span, and in what comes back.

Porting a loop of solves

Cubie directly replaces a loop of solve_ivp calls. You pass all of the input values to one solve call, and cubie solves every run in parallel on the GPU. You can usually use the same function in both libraries. SciPy passes the values in args= to your function’s extra arguments in order; cubie passes them by matching their name to a key in parameters=.

SciPy
import numpy as np
from scipy.integrate import solve_ivp

def van_der_pol(t, y, mu):
    return [y[1], mu * (1 - y[0] ** 2) * y[1] - y[0]]

mus = np.linspace(0.5, 4.0, 10000)
t_eval = np.linspace(0.0, 20.0, 201)
t = np.empty((201, 10000))
y = np.empty((201, 2, 10000))
for i in range(10000):
    sol = solve_ivp(
        van_der_pol,
        (0.0, 20.0),
        [1.0, 0.0],
        args=(mus[i],),
        method="RK45",
        t_eval=t_eval,
    )
    t[:, i] = sol.t
    y[:, :, i] = sol.y.T
cubie, with the same function
from cubie import solve_ivp

result = solve_ivp(
    van_der_pol,
    y0={"y1": 1.0, "y2": 0.0},
    parameters={"mu": mus},
    method="ode45",
    duration=20.0,
    save_every=0.1,
    output_types=["state", "time"],
)
t = result.time
y = result.state

Key changes:

  • Parameters by name: give the parameter values in a dict in parameters=, keyed by your function’s argument names, instead of in args=. cubie runs once for each value in the array.

  • Named starting values: give y0 as a dict with an entry for each state. cubie sorts the state columns by name, so name the states y1 and y2 to keep SciPy’s order.

  • Time: instead of t_span, give the total integration time as duration, and a start time as t0 if it isn’t 0. Instead of t_eval, give the time between saved points as save_every. Without save_every, cubie saves only the first and last points.

  • cubie returns every run’s results in one array, inside a SolveResult. Index the array by time first, then state, then run; see Working with Results. Add "time" to output_types to get the time points.

  • If you supply arrays for several parameters or initial values, cubie runs every combination of the supplied values by default. See Inputs and Parameter Sweeps for the other options.

Note

SciPy’s default relative tolerance is 1e-3, and Cubie’s is 1e-6. Results will not match unless these are the same. Even when the tolerances do match directly, there will be differences due to numerical precision (float32 vs float64) and due to the way that floating point math is carried out on GPUs vs CPUs. Even though the results do not match exactly, comparing each one to a much more accurate solution (solved to a much tighter tolerance) will show that Cubie’s and SciPy’s results are equally wrong.

What your function can contain

SciPy calls your function, so you can use anything Python allows in it. cubie reads your function and turns it into GPU code instead, so you can only use arithmetic, maths functions such as np.sin or math.exp, if/else, and for loops over a fixed range(...). You can’t use:

  • while loops or list comprehensions.

  • NumPy array functions such as np.array or np.zeros. Return the derivatives as a list or a tuple.

  • Variables defined outside your function. Add them as arguments and give their values in parameters=.

  • Anything that isn’t maths, such as printing or reading files.

Not supported

  • cubie has no equivalent of dense_output or event functions.

  • cubie saves solutions at a regular interval set by save_every, not at arbitrary t_eval points.
